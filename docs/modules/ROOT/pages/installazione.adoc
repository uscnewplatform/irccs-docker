= Installazione e Avvio
:description: Guida passo-passo per la prima installazione della piattaforma IRCCS su un nuovo host.

== Prerequisiti

Prima di procedere, assicurarsi che siano installati sul sistema:

* **Docker** e **Docker Compose**
* **Git**
* **OpenSSL** (`openssl`, `openssl-dev`)
* **OpenSSH** (`openssh`)
* Una chiave SSH valida per accedere al repository Git
* Accesso al registro Docker privato Nexus: `nexus.infocube.it`

[TIP]
====
Per effettuare il login al registro Nexus:

[source,bash]
----
docker login nexus.infocube.it
----

Le credenziali vanno richieste al team di sviluppo.
====

== Installazione su Alpine Linux / Proxmox

Per installazioni su container Proxmox con Alpine v3.22, eseguire i seguenti comandi:

[source,bash]
----
apk update && apk upgrade
apk add docker docker-compose
rc-service docker up
rc-service docker start
rc-update add docker
----

Configurare il daemon Docker con log rotation e storage driver:

[source,bash]
----
mkdir -p /etc/docker
cat > /etc/docker/daemon.json << EOF
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "20m",
    "max-file": "3"
  },
  "storage-driver": "vfs"
}
EOF
rc-service docker restart
apk add git
apk add openssl openssl-dev openssh
----

== Avvio rapido del progetto

[source,bash]
----
git clone git@github.com:infocube-it/irccs-docker.git
cd irccs-docker
cp .env_example .env
# Compilare il file .env con i valori forniti dal team di sviluppo
docker compose up -d
----

[WARNING]
====
Il file `.env` contiene credenziali riservate e **non deve mai essere committato** sul repository Git.
Il file `.env_example` fornisce il template con i nomi di tutte le variabili richieste.
====

== Configurazioni post-avvio

Due gruppi di step, in ordine: prima quelli manuali via UI Keycloak, poi
un unico comando che carica tutti i dati FHIR necessari.

=== A. Step manuali (UI Keycloak)

==== A.1 Configurazione SMTP in Keycloak

. Accedere alla dashboard Keycloak all'indirizzo `http://<host>:9445`
. Autenticarsi con le credenziali di admin definite nel file `.env`
. **Cambiare immediatamente la password** dell'utente admin e assegnargli il ruolo `ADMIN`
. Selezionare il realm `pascale`
. Nel menu laterale: *Realm Settings* → tab *Email*
. Inserire i parametri SMTP forniti dall'infrastruttura
. Verificare la connessione con il pulsante *Test connection*

==== A.2 Configurazione lingua e tema Keycloak

. Accedere alla UI di Keycloak (`http://<host>:9445`)
. Selezionare il realm `pascale` → *Realm Settings*
. Tab *Languages*: aggiungere **Italiano**
. Tab *Themes* → *Custom Theme*: selezionare `pascale-theme`

==== A.3 Rinnovo/Cambio Client Secret Keycloak

Se si rigenera il client secret di Keycloak:

. Accedere a: Realm `pascale` → *Clients* → `irccs` → *Credentials* → *REGENERATE CLIENT SECRET*
. Copiare il nuovo secret
. Aggiornare la variabile `KEYCLOAK_CLIENT_SECRET` nel file `.env`
. Riavviare lo stack:

[source,bash]
----
docker compose down
docker compose up -d
----

==== A.4 Verifica account di servizio Keycloak

Verificare che l'utente di servizio `service-account-irccs` nel realm `pascale` abbia il ruolo `/admin` (necessario per le operazioni di signup).

=== B. Step automatici — un solo comando

Dopo l'avvio dello stack, tutto ciò che si può automatizzare è lanciato in ordine da un unico installer a fasi. Stampa cosa fa, chiede conferma prima di ogni fase (`--yes` per saltare) ed è riprendibile (`--from N`, `--only N`, `--skip N`). La guida con l'elenco completo degli script è in `setup/README.md`.

[source,bash]
----
cd irccs-docker
ADMIN_PASS=<password admin Keycloak> ./setup/install.sh --hapi-url http://localhost:8080/fhir --kc-url http://localhost:9445
# con Zammad, audit e monitoraggio:
ADMIN_PASS=... ZAMMAD_TOKEN=... WEBHOOK_SECRET=... \
  ./setup/install.sh --zammad-url https://<zammad> --with-audit --with-ops
./setup/install.sh --dry-run        # mostra i comandi senza eseguirli
----

[cols="1,2,3"]
|===
|Fase |Cartella |Cosa fa

|10 |`setup/10-keycloak/` |Ruoli e autorizzazioni che il realm-export non contiene (audit, DocumentReference, farmacovigilanza, blocco ticket CRF, Zammad, tipi FHIR instradati)
|20 |`setup/20-fhir/` |SearchParameter custom, Patient Journey J-LI, registry dei tipi di consenso
|30 |`setup/30-terminologie/` |Librerie CRF (CTCAE v4/v5/v6, PRO-CTCAE, EORTC, EuroQol, USC PROFFIT) e farmaci AIFA (dati in `data-import/`)
|40 |`setup/40-zammad/` |Solo con `--zammad-url`: attributi dei ticket, webhook e trigger delle email, spegnimento delle email native, controlli
|50 |`setup/50-audit/` |Solo con `--with-audit`: partizione AUDIT, SearchParameter, trigger di immodificabilità, pgaudit
|60 |`setup/60-monitoraggio/` |Solo con `--with-ops`: cron di archiviazione Loki e backup DB (richiede sudo)
|===

Ogni script è idempotente: rieseguire l'installer dopo un'interruzione non duplica nulla. I segreti (`ADMIN_PASS`, `ZAMMAD_TOKEN`, `WEBHOOK_SECRET`) si passano solo dall'ambiente, mai come argomento.

I tipi di consenso sono un *registry dinamico* persistito come `CodeSystem` FHIR (`urn:irccs:consent-type`) — necessario per far comparire i tipi nel designer studi e per garantire che il tipo `privacy` esista. Successivamente sono gestibili a runtime dalla dashboard (Back-office → Tipi di consenso, solo SuperAdmin).

Per i dettagli sulle librerie CRF vedere xref:librerie-crf.adoc[Librerie CRF — Gestione e Import].

=== B2. Attributi personalizzati Zammad (ticketing)

Se il modulo ticketing (Zammad) è attivo, su ogni istanza Zammad nuova vanno creati gli *attributi personalizzati* (Object Manager) usati dalla dashboard. È la fase 40 di `setup/install.sh` (con `--zammad-url`); si può lanciare anche da solo. Agisce su Zammad, non su HAPI, e richiede un token admin Zammad.

[source,bash]
----
cd irccs-docker
ZAMMAD_TOKEN=<token admin Zammad> ./setup/40-zammad/install_zammad_attributes.sh https://<zammad>
----

* Il token va passato come variabile d'ambiente (non come argomento, per non lasciarlo in history/`ps`) e deve appartenere a un utente con permesso `admin.object`.
* L'URL è la radice di Zammad; il suffisso `/api/v1` viene aggiunto dallo script.
* Lo script è *idempotente*: gli attributi già presenti vengono saltati e la migrazione dell'Object Manager viene sempre rieseguita (copre un giro interrotto).

[cols="1,3"]
|===
|Oggetto |Attributi creati

|Ticket |`crf`, `crfdisplay`, `careplan`, `careplandisplay`, `patient`, `patientdisplay`, `patientjourneydisplay`, `directlink`
|Group |`organization`
|===

[IMPORTANT]
====
Senza questi attributi Zammad *scarta in silenzio* i campi inviati alla creazione del ticket: il ticket nasce senza collegamento a paziente/CRF/percorso e il contatore ticket della dashboard (che raggruppa per `patientjourneydisplay`) non lo conta. I ticket creati prima dell'installazione degli attributi restano senza questi campi.
====

Il microservizio Zammad verifica la presenza degli attributi Ticket all'avvio (log `ERROR` con l'elenco di quelli mancanti) e rifiuta con *HTTP 422* la creazione di un ticket che usa un attributo assente. Il token del microservizio deve avere il permesso `admin.object` perché la verifica funzioni; senza, la verifica viene saltata con un warning.

Lo stato ticket "annuncio", il trigger «presa in carico alla risposta», le impostazioni e l'indirizzo mittente sui gruppi li applica `setup/40-zammad/apply_zammad_config.sh` dalla configurazione salvata in `setup/40-zammad/config/` (fotografia ripulita di produzione; vedi il README di quella cartella). Dopo gli script restano manuali: il canale SMTP, il login SSO e la valorizzazione di `organization` sui gruppi `annunci_*` (vedi la documentazione del microservizio Zammad).

=== C. Import terminologia LOINC (opzionale, MANUALE)

Per abilitare la validazione e ricerca di codici LOINC nel server FHIR è necessario importare la terminologia.

[IMPORTANT]
====
A partire da LOINC 2.77, il file `MultiAxialHierarchy.csv` è stato rimosso e sostituito da `ComponentHierarchyBySystem.csv`. Tutti i file sono inoltre racchiusi in una cartella con il numero di versione (es. `Loinc_2.82/`). +
Il file `terminology/loincupload.properties` nel repository gestisce già questi mapping — non modificare i path di default senza aggiornare anche questo file.
====

==== Prerequisiti

* Account su https://loinc.org (registrazione gratuita)
* File `Loinc_<version>.zip` scaricato dalla sezione *Downloads* di loinc.org
https://loinc.org/download/loinc-complete/

* `hapi-fhir-cli.jar` della stessa versione del server (es. 8.6.8)
https://github.com/hapifhir/hapi-fhir/releases/download/v8.6.8/hapi-fhir-8.6.8-cli.zip


==== Procedura

Copiare zip, properties e CLI nel container (il CLI **deve girare dentro il container** perché i file > 10 MB vengono referenziati localmente, non trasferiti via HTTP):

[source,bash]
----
docker cp Loinc_2.XX.zip irccs-hapi-fhir:/tmp/
docker cp terminology/loincupload.properties irccs-hapi-fhir:/tmp/
docker cp terminology/hapi-fhir-cli.jar irccs-hapi-fhir:/tmp/
----

Eseguire l'import:

[source,bash]
----
docker exec irccs-hapi-fhir java -jar /tmp/hapi-fhir-cli.jar upload-terminology \
  -d /tmp/Loinc_2.82.zip \
  -d /tmp/loincupload.properties \
  -t http://localhost:8080/fhir \
  -v r4 \
  -u http://loinc.org
----

[NOTE]
====
L'operazione richiede 15-30 minuti. Monitorare i log in un secondo terminale:

[source,bash]
----
docker logs -f irccs-hapi-fhir
----

Completamento confermato da risposta HTTP 200 con `OperationOutcome` di severity `information`.
====

Per aggiornare a una versione LOINC successiva, aggiornare il prefisso di versione (es. `Loinc_2.82` → `Loinc_2.83`) in tutte le righe del file `terminology/loincupload.properties`.

== Abilitazione SSL per Keycloak

Per attivare Keycloak in modalità SSL:

. Fornire certificato e chiave privata tramite volume Docker, riportandoli nel file `keycloak.conf`
. Rimuovere il flag `--start-dev` dall'entrypoint nel `docker-compose.yaml`
. La porta HTTPS di Keycloak passa da `9445` (HTTP) a `8443` (HTTPS)

[NOTE]
====
In ambiente di test può essere necessario aggiungere l'hostname di Keycloak in `/etc/hosts`:

[source]
----
127.0.0.1 keycloak.irccs.infocube.it
----
====

== Disabilitazione del sistema di ticketing

Per disabilitare il modulo Zammad, commentare o rimuovere la variabile `VITE_APP_ZAMMAD_HOST` nel file `httpd-config/config-prod.js`. Questo nasconderà i pulsanti di gestione delle Query e bloccherà le chiamate di polling.
