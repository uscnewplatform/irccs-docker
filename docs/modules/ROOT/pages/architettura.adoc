[cols="1,2"]
|===
| Componente | Tecnologia

== Pattern di sicurezza

=== JWT e OIDC

Tutti i microservizi validano il Bearer token JWT emesso da Keycloak tramite:
[source,properties]
----
quarkus.oidc.token.issuer=${OIDC_TOKEN_ISSUER}
quarkus.oidc.token.verification=jwt
quarkus.oidc.application-type=service
----

=== Keycloak Policy Enforcer

Il `policy-enforcer` di Quarkus verifica per ogni request se l'utente ha il permesso di accedere alla risorsa FHIR con il metodo HTTP richiesto (usato come scope):
[source,properties]
----
quarkus.keycloak.policy-enforcer.enable=true
quarkus.keycloak.policy-enforcer.http-method-as-scope=true
----

=== Groups-IDs e visibilità

Ogni risorsa FHIR è taggata con `group_ids` corrispondenti all'organizzazione dell'utente che l'ha creata. L'interceptor `FhirInterceptor` (libreria `i3-annotations`) filtra automaticamente i risultati in base ai gruppi del JWT dell'utente.

I microservizi di sistema (es. `irccs-microservice-crf-tac`) usano il **service account** Keycloak per bypassare il filtro `group_ids` nelle operazioni interne.

== Interceptor CDI — catena di elaborazione

[source]
----
HTTP Request
  → [Keycloak Policy Enforcer] verifica permesso
  → AuthFlowInterceptor (@AroundInvoke, @SyncAuthFlow)
    → FhirInterceptor.intercept(fhirClient, context)
      → Flow specializzato (PatientFlow / PractitionerFlow / Flow default)
        → context.proceed() → metodo del controller
          → FhirClient<T> → HAPI FHIR Server
----
